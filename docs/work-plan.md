## 1. 범위 점검 결과

이번 개발 범위의 목적은 PRD의 올해 말 성공 모습인 **"부서장이 내년 상반기 2~3곳 시범을 승인한다"**입니다. 기능을 더 넣는 것이 아니라, 시연에서 보여줄 두 장면(1분 등록, 12곳 한 화면)을 믿을 수 있게 다듬고 실제 사람으로 확인하는 것이 남은 일입니다.

| 구분 | 내용 | 처리 |
|---|---|---|
| PRD 핵심 기능 3개 | 구현·테스트 완료 (FR 26개 중 24개 충족) | 유지 |
| 범위 초과 | "7일 넘게 멈춤" 경고(FR-LIST-06, FR-HQ-07). PRD는 처리 속도를 범위 밖으로 정함 | Q1 결정(뺀다) → T3 |
| 품질 빈칸 | 저장 실패가 조용히 묻힘, 사진 장수 상한 없음(NFR-REL-02 미충족) | T1 |
| 테스트 빈칸 | 명세의 경계 조건 일부가 테스트되지 않음 | T2 |
| 목표 검증 빈칸 | "1분", "30분", "3분 시연"을 실제 사람으로 확인한 적 없음(MAN-01~03) | T4 → T5 |
| 성공 지표 빈칸 | 시범 전 기준값(취합 시간, 재문의 전화)이 기록돼 있지 않음 | T6 |
| 범위 밖 유지 | 로그인·서버·사내망, 입주민 알림, 엑셀 내려받기, 업체 배정 상세 | OUT-01~05 |

### T1. 저장 실패를 알리고 사진 장수를 제한한다 — [#2](https://github.com/HeyonSeo/PRD_TEAM_test/issues/2)
- **목적**: 등록 완료가 떴는데 본부에 안 가고 새로고침하면 사라지는 "조용한 실패"를 없앤다. 엑셀 대신 쓰려면 도구를 믿을 수 있어야 한다(PRD 5 핵심 지표).
- **요구사항**: NFR-REL-02(주), FR-REG-01, FR-REG-07
- **포함**
  - `store.add`가 저장 성공 여부를 돌려줌. 쓰기 실패 시 메모리 반영을 되돌림
  - `field.html`: 실패하면 "저장하지 못했습니다. 사진 수를 줄여 다시 눌러 주세요"를 띄우고, 입력은 유지하고, 완료 화면은 띄우지 않음
  - 사진 10장 상한(A1). 넘으면 10장까지만 받고 안내
  - `requirements.md`의 NFR-REL-02 상태를 `충족`으로, FR-REG-01 경계 조건 갱신
- **제외**: 오래된 접수 자동 정리, 서버 저장, `store.setStatus` 실패 처리(상태 변경은 데이터가 작아 실패 가능성 낮음. 필요하면 별도 작업)
- **선행 작업**: 없음
- **검증**: 새 테스트 `[7]` → NFR-REL-02, FR-REG-01에 연결
  - setItem 실패를 흉내 낸 상태에서 등록 → 실패 안내, 완료 화면 없음, 저장소 건수 그대로, 입력 유지
  - 사진 11장 선택 → 10장만 남고 안내
  - 기존 169개 통과, 추적성 문제 0건
- **데이터 변경**: 저장 형식·키 변경 없음. `store.add` 반환 약속만 바뀜(성공 시 접수, 실패 시 `null`). 호출하는 곳은 `field.html` 한 곳
- **위험**: 브라우저 용량 초과를 테스트에서 그대로 재현하기 어려움 → setItem을 실패하도록 바꿔 끼워 검사
- **예상 크기**: S (반나절, 변경 50~80줄)

### T2. 명세의 경계 조건을 테스트로 덮는다 — [#3](https://github.com/HeyonSeo/PRD_TEAM_test/issues/3)
- **목적**: 명세에는 있지만 테스트가 없는 경계 조건을 확인해, 시연 중 예상 밖 동작을 미리 찾는다.
- **요구사항**: FR-REG-01, FR-REG-03, FR-REG-05, FR-REG-06, FR-LIST-02, FR-HQ-05
- **포함**: 테스트 `[8]` 추가
  - 한 줄 내용 60자 넘게 입력 안 됨, 공백만이면 등록 불가
  - 이미지가 아닌 파일은 무시
  - 동을 바꾸면 고른 호가 풀림
  - 검색: 숫자 없음 → 전체, `1011203` 붙여 쓰기, 짧은 검색어
  - 한 번에 6건 이상 바뀌면 본부에서 강조 안 함
- **제외**: 동작 변경. 테스트가 명세와 다르게 나오면 이 작업에서 고치지 않고, 명세를 고칠지 코드를 고칠지 별도 이슈로 나눈다.
- **선행 작업**: 없음(T1과 병렬 가능)
- **검증**: 새 테스트가 모두 통과하고 각 요구사항에 연결됨. 추적표에서 해당 요구사항의 테스트 수가 늘어남
- **데이터 변경**: 없음
- **위험**: 명세와 실제 동작의 차이가 나오면 후속 작업이 생김
- **예상 크기**: S (테스트 30~60줄)

### T3. "7일 넘게 멈춤" 경고를 뺀다 (Q1 = 뺀다) — [#7](https://github.com/HeyonSeo/PRD_TEAM_test/issues/7)
- **목적**: PRD 범위(처리 속도는 범위 밖)에 맞추고, 시연 메시지를 "자동 취합"에 집중시킨다.
- **요구사항**: FR-LIST-06, FR-HQ-07 → 상태를 `범위 밖`으로 옮김(OUT-07 신설)
- **포함**
  - 현장: "⚠ 멈춤" 표시 제거, 경과 일수(FR-LIST-05)는 유지
  - 본부: 카드 경고, 위쪽 "7일 넘게 멈춤" 합계, 상태 필터의 "7일 넘게 멈춤", 표의 "⚠ N일 멈춤" 제거
  - 테스트: `[3]`·`[4]`의 경고 테스트 3개를 "경고가 나오지 않음" 테스트 `[9]`로 바꿈(결정에 따른 의도적 교체)
  - 문서: 요구사항 명세, 아키텍처(4절, 다이어그램 03), `mockup/README.md` 대본에 "처리 속도는 시범 뒤 별도 논의" 한 줄 추가
- **제외**: 시드 데이터 변경, 다른 화면 개편
- **선행 작업**: 없음(Q1 결정 완료). T1·T2와 병렬
- **검증**: `[9]` 현장·본부 어디에도 "멈춤" 문구가 없음, 경과 일수는 그대로 보임. 전체 통과, 추적성 문제 0건
- **데이터 변경**: 없음(표시만)
- **위험**: 부서장이 "처리가 늦은 건은 어떻게 보느냐"고 물을 수 있음 → 대본에 답을 넣어 대응
- **예상 크기**: S

### T3′. (Q1 = 유지일 때 T3 대신) 경고 기준을 맞추고 시드를 조정한다 — 취소됨, 기록용
- **목적**: 경고를 유지하되, 시연 화면이 "현장 처리 지연"으로 읽히지 않게 한다.
- **포함**: 7일 기준을 `LH_DATA` 한 곳으로 모음(지금은 `field.html`·`hq.html`에 따로 있음). 시드 날짜를 조정해 경고 단지가 2~3곳이 되게 함. FR-LIST-06·FR-HQ-07의 상태를 `충족`으로 바꿈
- **선행 작업**: Q1 결정
- **검증**: 시드 상태에서 경고 카드 2~3개, 기존 경고 테스트 통과
- **데이터 변경**: **있음.** 시드 생성 규칙이 바뀌므로 시연 전에 "시연 데이터 초기화"가 필요함
- **위험**: 과장 채택 위험은 그대로 남음
- **예상 크기**: S

### T4. 수동 검증 키트를 만든다 — [#5](https://github.com/HeyonSeo/PRD_TEAM_test/issues/5)
- **목적**: 자동 테스트로는 알 수 없는 목표 달성 여부(1분 등록, 30분 확인, 3분 시연)를 같은 방식으로 재고 기록할 수 있게 한다.
- **요구사항**: MAN-01, MAN-02, MAN-03 (G-01, G-02, G-04)
- **포함**: `docs/validation/`에 기록 양식 3개
  - 참가자, 날짜, 걸린 시간, 막힌 지점, 첫 인상 한 줄, 통과 여부
  - 진행자 안내: 설명 없이 처음 쓰게 하기, 사진 준비, 초기화 순서
  - 결과를 `requirements.md`의 MAN 상태와 추적표에 반영하는 방법
- **제외**: 실제 검증 실시(T5)
- **선행 작업**: T1(#2), T3(#7). 화면이 확정된 뒤의 기준으로 재야 함(양식 작성 자체는 먼저 해도 됨)
- **검증**: 양식 3개가 있고, 동료 1명이 양식만 보고 진행 순서를 설명할 수 있음
- **데이터 변경**: 없음
- **위험**: 낮음
- **예상 크기**: XS

### T5. 수동 검증과 시연 리허설을 한다 — [#6](https://github.com/HeyonSeo/PRD_TEAM_test/issues/6)
- **목적**: 부서장 시연 전에 두 장면이 실제 사람에게 통하는지 확인한다.
- **요구사항**: MAN-01, MAN-02, MAN-03
- **포함**: 과장 1~2명 등록 시간 측정(A3), 본부 확인 시간 측정, 리허설 1회와 첫 인상 기록, 결과에 따라 MAN 상태 갱신
- **제외**: 실제 시범 운영
- **선행 작업**: T4(및 T1, T3)
- **검증**: 기록지 3개가 채워짐. 과장이 60초 안에 등록, 본부 확인 30분 안, 리허설 3분 안, 첫 인상이 "취합이 자동" 쪽
- **데이터 변경**: 없음(가짜 데이터만 사용)
- **위험**: 과장 일정 확보. 처음 쓰는 사람이 60초를 넘기면 등록 화면 개선 작업이 새로 생김
- **예상 크기**: S (실시 1~2일, 개발 아님)

### T6. 시범 전 기준값을 기록한다 — [#4](https://github.com/HeyonSeo/PRD_TEAM_test/issues/4)
- **목적**: 시범 6개월 뒤 "취합 주 1일 → 30분", "재문의 하루 3~4통 → 1~2통"을 비교할 수 있게 지금 상태를 잰다. 지금 재지 않으면 나중에 효과를 증명할 수 없다.
- **요구사항**: OUT-06(시범 지표 측정) 중 기준값 부분, PRD 5
- **포함**: 2주 동안 주간 취합 시간, 하루 재문의 전화 수, 단지별 접수 경로(전화·방문·엑셀·메일)를 기록(A4)
- **제외**: 시범 중 측정 도구 개발
- **선행 작업**: 없음(지금 바로 시작 가능, 개발과 독립)
- **검증**: 2주 기록이 남아 있고, 평균값이 PRD 5에 적힌 값(주 1일, 하루 3~4통)과 비교돼 있음
- **데이터 변경**: 없음. 실제 업무 기록이므로 개인정보(입주민 이름·연락처)는 적지 않음
- **위험**: 바쁜 주에 기록을 빠뜨림 → 하루 끝 1분 기록으로 단순화
- **예상 크기**: XS (하루 1분 × 2주, 개발 아님)
